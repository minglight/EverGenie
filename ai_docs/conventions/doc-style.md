# 文件寫法與內容分工

Status: DRAFT — 2026-10-23 改寫自參考專案的 `ai_docs/conventions/doc-style.md`，pending author review.

`ai_docs/` 有三種文件（加上路由用的 `INDEX.md`）。這份規定每種放什麼、怎麼互相引用、長什麼樣子。寫或改 `ai_docs/` 底下任何文件前先讀。

| 檔案 | 只回答一個問題 | 內容 | 機器可檢查 |
|---|---|---|---|
| `INDEX.md` | 「這件事要讀哪幾份？」 | 路由 | 部分（模組清單 vs registry） |
| `conventions/*.md` | 「做這件事的規矩是什麼？」 | 跨模組的規則 | 否，靠 review |
| `modules/*.md` | 「這個模組有什麼、額外有什麼限制？」 | 事實表＋模組自己的規則 | 是（P1 起對照程式） |
| `schemas/*.md` | 「這種資料存成什麼樣子？」 | 路徑、欄位、連結、保存規則 | 是（P2 起對照 vault 驗證器） |

## MUST
- **DOC-1** — 每個事實只有一個家。加一段話之前，先在下面「內容歸屬」找到它的位置。
- **DOC-2** — 步驟和流程（「新增一個套件的三步」）只放 `conventions/`。
- **DOC-3** — 清單（RPC 方法、事件、檔案種類、排程、依賴）只放所屬模組的卡。
- **DOC-4** — 模組自己的規則放那張卡，且附依據：`Evidence: <檔案> → <符號>`＋守它的測試名稱（2026-10-30 起不標 REQ）。
- **DOC-5** — 「哪個模組負責哪件事」只寫在 `architecture.md` 的「底層模組」「業務塊」「資料種類的擁有者」三張表（2026-11-02 S8-5 從 `INDEX.md` 搬過去：那三張表是 depcheck 的設定，不另抄一份）。
- **DOC-6** — 引用程式寫「檔案路徑＋符號名稱」（`internal/base/vault/store.go` → `Store.Put`）；不是符號就引一段 grep 得到的字串。
- **DOC-7** — 規則編號永久不改、不重用；每份文件有自己的前綴（`DOC-`、`VLT-`、`BUS-`…），`N` 代表禁止（`VLT-N2`）。幾張卡合成一張時，原來的前綴都留在那張卡、編號不重編（一張卡可以有多個前綴）；新規則接在其中一個前綴的下一個沒用過的號碼。兩份文件撞同一個前綴時，改引用少的那邊的前綴、號碼不變（例 doctor 的 DOC-n → DCT-n）。
- **DOC-8** — 樣板的每一段都要有；沒東西寫就寫 `None.`，讓「確認是空的」跟「還沒寫」分得出來。
- **DOC-9** — 寫給作者看的段落（法律、設計決定、review 版）用繁體中文白話；識別字、路徑、指令保持英文原樣。
- **DOC-10** — 說明卡「依賴」段用反引號寫的內部模組（`platform`、`vault`、`app`、`base/agent/personaref`…），就是標題那個套件（含子套件）正式程式碼 import 的，一個不多、一個不少；經 `Deps` 小 interface 注入、不 import 的寫白話、不加反引號。doccheck 比對（測試檔不算）。
- **DOC-11** — 每個業務塊（`internal/feature/<塊>`）剛好一張說明卡 `modules/<塊>.md`，標題寫 `internal/feature/<塊>`；塊裡的子套件不另開卡，寫成那張卡裡的分段（`### <子套件>`）。底層模組一個一張（子套件併進母模組那張，例外是很大的 `app/board`）。doccheck 擋（2026-11-02，S8-4）。
- **DOC-12** — 跟著發行檔帶的文件只有一份清單 `ai_docs/bundled.txt`（DEV-155；platform 卡 PLT-28：`scripts/dist.sh` 照它帶、`evergenie docs` 照它給）。帶的標準是「秘書替主人做套件、跟主人解釋套件怎麼運作會讀到的」，內部開發用的（發版、部署、runbooks、說明卡、開發流程、這份）不帶。帶的文件提到別的 ai_docs 文件（連結或寫出檔名）時，那份也要在清單上；沒帶的就改寫成不寫路徑的說法（「說明卡 packages 的 PKG-30」「開發流程規範的 DEV-12」）。秘書會讀到的文字（跟著發行檔的原始碼與文字全文：官方套件——`dev_only` 的除外——的每個檔、`sdk/` 的 `.go`，含註解；核心內嵌的 `.md`；核心 Go 正式程式碼的字串；看板原始碼不是註解的行）不寫 `ai_docs/…`，也不寫沒帶的 `conventions|schemas|modules|runbooks/*.md`；指文件一律寫 `evergenie docs show <清單上的一份>`，沒帶的寫成「schema task」「說明卡 packages」這種不寫路徑的說法。帶的文件會被主人那台的秘書讀到：不寫主人的私事、家的路徑、密碼、內部網址（單號可以留）。doccheck 擋路徑與清單（2026-11-14）；私事靠寫的人與審查。

## NEVER
- **DOC-N1** — 不引行號。行號幾週就會偏掉，而且偏掉時讀的人不知道自己被帶錯地方。
- **DOC-N2** — 「現在還做不到」不寫成 MUST／NEVER，放 `## 已知限制` 並附目前的替代做法；寫成禁止，AI 會發明扭曲的繞法。
- **DOC-N3** — 規範文件不連到個別說明卡（加模組就得改規範）；只有 `INDEX.md` 連到卡。
- **DOC-N4** — 沒有依據的規則不寫進卡；寫 `None.`。
- **DOC-N5** — 不重述別份文件的規則；一句話指出是哪份就好。
- **DOC-N6** — 不寫事故故事（作者的偏好）：只寫規則與現況。

## 內容歸屬
| 資訊 | 家 | 其他地方 |
|---|---|---|
| 怎麼做 X 的步驟 | `conventions/<主題>.md` | 只寫文件名 |
| 模組的 RPC／事件／檔案種類／排程／依賴 | 那張卡 | 規範最多放一段範例 |
| 只適用一個模組的限制 | 那張卡的 MUST／NEVER | — |
| 一種資料的欄位與保存規則 | `schemas/<種類>.md` | 卡只寫「儲存：見 schema」 |
| 系統要做到的事 | task 的驗收條件＋測試名稱（2026-10-30 起不再有 REQ 表） | 卡的不變條件寫守它的測試名稱 |
| 為什麼這樣設計（設計決定 D-n） | 負責那件事的規範或說明卡的 `## 設計決定`（放在 `## 已知限制` 前；沒有就不用這段） | 引 D-n；編號永久不改、不重用，只定義一次（doccheck 擋） |
| 整個 project 的底線 | 憲法、EverGenie 的宗旨與法律（作者的私人文件庫，不公開、不在 repo） | 引「法律第 n 條」 |
| 只有作者能決定的事 | 該份規範的 `## 待作者決定` | 卡不放這段；跟著發行檔帶的文件（DOC-12）也不放 |

## 引用方向（單向）
```
INDEX.md ──→ conventions/*.md ──→ 程式（檔案＋符號）
   └──────→ modules/*.md ──→ schemas/*.md、sdk/
```

## 樣板 A：規範（`conventions/*.md`）
```
# <標題>

Status: DRAFT — <來源>，pending author review.

<一兩句：涵蓋什麼、什麼時候要讀>

## MUST
- **<ID>** — <規則，一行>
## NEVER
- **<ID>** — <禁止，一行，附它防的是什麼>
## 範例
## 已知限制
## Handoff            （一行：接著讀哪份）
## 待作者決定        （必有，放最後；沒有就 None.；跟著發行檔帶的不放這段）
```

## 樣板 B：模組說明卡（`modules/*.md`）
```
# 模組：<名稱>（<套件路徑>）
Status: DRAFT — 設計 <日期>，pending author review.

**目的：** <一兩句>
**種類：** 核心模組 | 官方套件 | admin 套件

## MUST
## NEVER
## 職責
## 不負責             （容易被誤以為歸這裡的事，寫明歸誰）
## 介面               （API 服務與方法、Go interface 簽名）
## 事件               （發出／訂閱的 bus 事件）
## 儲存               （指到 schemas/）
## 依賴               （只能是 architecture.md 允許的方向；反引號＝正式程式碼真的 import，DOC-10）
## 錯誤               （會回哪些錯誤碼、什麼時候）
## 不變條件
## 測試計畫
## 已知限制
```
說明卡的標題跟 `Status:` 之間不空行（跟樣板 A 不同，故意的）。

## Handoff
寫規範讀樣板 A，寫說明卡讀樣板 B。

## 待作者決定
None.
