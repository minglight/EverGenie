**目的：** 角色的衣服：用點數兌換、輪播出場、設計中草稿；沒兌換的只看得到剪影（伺服器不送真的圖）；現在穿哪一套決定角色的頭像與影片。看板上兩頁：**衣櫃**＝擁有的衣服（現在穿哪套、「現在穿這套」、輪流穿；CLO-30）；**展示間**＝所有衣服、用點數兌換、新增角色與加衣服的入口（開到核心的角色頁，CLO-14、15、20）。設計中的衣服在開發家角色頁的「修改」分頁審（CLO-35），一般家看不到（CLO-37）。
**種類：** 官方套件（`kind = "program"`：背景行程處理兌換請求、輪播換衣、維護公開資料夾，並把每位角色的檢視寫回 vault；仍然**沒有 RPC**，D-28）

**家的佈局（DEV-145）：** 本檔的路徑照第 1 版的家寫。第 2 版（`home.toml` `[layout] version = 2`）的公開資料夾 `runtime/packages/closet/public/` 在家外面狀態資料夾的 `runtime/`，官方角色卡與官方圖（`personas/<代號>.md`、`personas/avatars/`）在狀態資料夾的 `personas/`；`home.toml` `[layout] official_personas = "home"`（relayout 預設）時官方角色仍在家裡的 `personas/`；主人的 `personas/mine/` 仍在家裡。程式用 `sdk.RuntimeDir`、`sdk.OfficialPersonasDir`；角色的顯示名讀卡走找官方卡的共用入口 `sdk.OfficialCardPath`（官方角色資料夾先、沒有才用跟著程式的公開卡 `EVERGENIE_BUNDLED_PERSONAS`，agents 的 PRS-25；主人有同代號的卡時跟著程式的那張不算、用主人的，PRS-27；測試 `TestPersonaNameBundledCard`、`TestPersonaNameMineBeatsBundledCard`）；隱藏版的 `dir` 是 `mine/` 開頭的在家裡的 `personas/` 找，其他在官方角色的位置找。

## MUST
- **CLO-1** — 衣櫃：用點數兌換、輪播出場、設計中草稿；沒兌換的只看得到剪影（伺服器不送真的圖）。規則的正本是 `internal/rules`（純函式，用 Go 重寫舊系統 `closet.py` 的概念）。
- **CLO-2** — 使用者自己的角色、衣服、照片（只收 PNG、JPEG、WEBP；可以設成免點數）；官方角色的衣服與兌換條件不能改。由**套件 `closet-mine`**（P6-4c，2026-11-03 起預設啟用，見 `closet-mine.md`）寫 `closet.outfit`（`source = mine`）與 `personas/mine/`；closet 自己只負責讀：圖在哪只看照片紀錄（`closet.photo` 的 `source`＋`file`，CLO-31、CLO-34）——`source = mine` 的 `file` 相對於 `personas/mine/`（DEV-160 S3 起新上傳的在 `photos/<照片編號>.<ext>`，新角色本身的頭像在 `avatars/<代號>.<ext>`；舊檔照舊在 `avatars/`、`avatars/full/`、`adult/`，紀錄指過去），檔名與資料夾不帶意思；`cost = 0` 就是免點數，`state = draft` 就是設計草稿。**全身照**（P6-4c）：`type = full` 的照片紀錄，只對擁有的與草稿的衣服公開成 `f/<人設>/<衣服>/1.<ext>`，沒擁有的不公開、也不給剪影；`person.outfits[]` 有 `full`（網址或空字串）與 `source`。
- **CLO-3** — 資料有十一種，都經 `vault`（YAML 標頭、一筆一檔，放 `vault/pkg/closet/<種類>/`，欄位見 `schemas/closet.md`）：`outfit`（目錄）、`unlock`（兌換紀錄）、`rotation`（輪播設定）、`request`（兌換請求，`Q-<n>`）、`person`（每位角色的檢視）、`state`（點數與隱藏版開關的檢視）、`variant`（隱藏版，CLO-17）、`note`（衣服意見，`CN-<n>`，CLO-22）、`photo`（照片，一筆一個檔，CLO-31）、`capabilities`（這個家支援什麼，CLO-32）、`action`（別的套件登記的動作，CLO-33）。**`unlock`、`person`、`state`、`capabilities` 只有套件的程式寫**；頁面與秘書只寫 `outfit`、`rotation`、`request`、`variant`、`note`、`photo`（頁面：角色頁「修改」分頁改 `photo` 的 `adopted`、`hidden`、`type`、`order`；秘書不改 `adopted`：換圖走 closet-mine 的換圖請求，開發家自動回到還沒採用，closet-mine 卡 CMI-18、CMI-25；新增照片紀錄是轉換器與 S3 起的上傳；**一般家的設計中我的衣服由程式自動上架**，CLO-38）；`action` 由登記的套件的秘書寫。
- **CLO-4** — 擁有：`cost = 0` 或有認得的 `unlock` 就擁有；`draft` 不算擁有也不能兌換；`retired`（下架）的衣服已擁有的人照樣有，沒擁有的看不到。
- **CLO-5** — 點數：可用點數 ＝ `habits.wallet/main.earned`（只增不減）減所有認得的 `unlock.cost`，最少 0；**不直接用 `wallet.points`**（habits 約 2 秒後才把剛花掉的算進 `spent`，用 `earned` 自己減才不會在這段空檔重複花）。`unlock` 只認 `by` 是 `closet` 或 `migrate`（搬家當天的轉資料腳本）的；別的來源寫的（頁面、秘書直接 `data add closet.unlock`）一律封存並記 log，免得繞過點數、也免得 habits 算錯 `spent`。
- **CLO-6** — 兌換請求（頁面或秘書寫 `closet.request`，程式驗證；頁面**不能**直接寫生效的 `unlock`）：依編號由小到大處理 `state = pending` 的。拒絕原因（白話，寫進 `reason`）：`by` 不是 `owner(…)` →「只有主人本人可以花點數兌換」；找不到那套或人設／衣服對不上 →「衣櫃裡沒有這套衣服」；草稿、沒擁有的下架 →「這套還不能兌換」；免費或已擁有 →「已經擁有這套了」；沒有錢包 →「還沒有點數：先安裝「習慣」套件、達標賺到點數才能兌換」；點數不夠 →「點數不夠：要 N 點，現在 M 點」。通過就寫 `unlock`（`by = closet`），並在 `person`、`state` 寫好之後才把請求標成 `done`＋`unlock`（所以看到 `done` 時頁面讀到的已經是兌換後的樣子）。
- **CLO-7** — 重播安全：行程重開後同一個 pending 請求再處理一次，結果相同、不重複扣點（`unlock` 編號＝衣服編號，一套只會兌換一次；已存在而且 `request` 欄位就是這筆請求，當作上次寫了一半、直接當成功）。同一輪裡的多個請求依序處理，每處理完一個就更新可用點數，所以不會有兩個請求同時扣點。兌換後不發通知（使用者自己按的）。
- **CLO-8** — 輪播：`hour = Unix 秒 / 3600`；有效清單 ＝ 勾的裡面還擁有的（照目錄順序），沒有就是第一套擁有的；穿第 `hour % len(有效清單)` 套；同一套有 n 張照片時穿第 `(hour / len(有效清單)) % n` 張（跟舊系統同一個算式）。主人指定「現在穿這套」而且時間還沒到時穿指定的那套、不看 `hour % len`（CLO-30；張數仍照同一個算式）。穿的那套沒有任何圖 → 不公開 `worn`（核心退回人設預設圖）。
- **CLO-9** — 公開資料夾 `runtime/packages/closet/public/`（只有這個行程寫，PKC-10；核心唯讀送出，D-29、REQ-175）：`o/<人設>/<衣服>/<n>.<ext>`（真圖，只放擁有的與 `draft` 的；`<n>.mp4` 是同張的動態）、`f/<人設>/<衣服>/1.<ext>`（全身照，只放擁有的與 `draft` 的，P6-4c）、`s/<人設>/<衣服>/1.png`（剪影，只給沒擁有的、非草稿、非下架的衣服，只做第 1 張）、`worn/<人設>.<ext>` 與 `worn/<人設>.mp4`（現穿那張）。**不變條件：沒擁有的衣服，真圖、全身照與影片的檔案在公開資料夾裡不存在**（唯一例外是開發家，CLO-27）。
- **CLO-10** — 剪影只用標準庫（`image`、`image/png`、`image/jpeg`）：解碼 → 透明處墊灰 → 轉亮度 → 面積平均成 16×16 → 雙線性放大成 128×128 → 亮度壓進 `[90,190]` → 灰階 PNG。輸出只由那 256 個平均值決定，細節（臉、字、輪廓）不可能還原。解不開的檔（WEBP、壞檔、寬×高超過 4000 萬像素）不產生剪影，`photos[0].url` 填空字串，頁面自己畫灰色人形。
- **CLO-11** — 行程：開機先做一輪；`vault.watch` 種類 `closet.outfit`、`closet.photo`（DEV-160）、`closet.rotation`、`closet.request`、`closet.unlock`、`closet.variant`、`habits.wallet`、`agent`，有變就去抖 1 秒再做一輪（官方角色包寫進官方層的衣服目錄也會發變更事件，VLT-19：新家同步完衣櫃馬上有衣服，DEV-157）；每個整點做一輪（輪播換衣、封存超過 7 天的已處理請求）；隱藏版時段的開頭與結尾各做一輪（晚 1 秒；那一輪中途失敗、邊界已過就隔 3 秒再試，CLO-17）；每 5 分鐘做一輪（有人把圖複製進家裡不會觸發 vault，靠這個發現、補登記照片紀錄，CLO-34）；訂閱斷線 3 秒後重連並補做一輪。一輪 ＝ ①清不認的兌換 ②處理待處理的請求 ③算 `person`／`state` ④對帳公開資料夾 ⑤內容有變才寫 `person`／`state`（`computed_at` 不算內容）⑥把成功的請求標成 `done`。錯誤寫 stderr，一筆壞資料略過那一筆。

資料在 `vault/pkg/closet/{outfit,unlock,rotation,request,person,state,variant,note,capabilities,action}/<編號>.md`（YAML 標頭）。公開資料夾 `runtime/packages/closet/public/`（可重建的衍生檔，附 `.state.json` 記每個檔案的來源簽章，來源沒變就不重寫）。`runtime/packages/closet/out.log` 是行程的 log。

## 錯誤
- 欄位不符 → vault 回 `INVALID` 並說明；`outfit` 的編號不等於 `<人設>-<衣服>`、人設或衣服 id 格式不合、`cost` 不是 0 以上整數 → 程式記一次 log 略過那一筆（不出現在 `person`）。
- 讀核心資料失敗 → 這一輪不寫任何東西、記 log，下一次變更或每 5 分鐘再試。
- 公開資料夾某個檔案做不出來（來源不是一般檔案、超過 30 MB、剪影解不開）→ 記一次 log，那個檔案不放，`person` 裡那張的網址留空或不列。
- 套件停用時十一種資料暫時看不到（`capabilities` 看不到＝核心與頁面當這個家什麼都不支援）；重新啟用資料回來（REQ-173）；套件沒在跑時請求不會被處理，頁面顯示「已送出，等衣櫃處理（套件沒在跑時會晚一點）」（兌換）或「已送出，等一下就會換好」（現在穿這套）。

## 不變條件
- 衣櫃：用點數兌換、輪播出場、設計中草稿；沒兌換的只看得到剪影（伺服器不送真的圖）。開發家（有 `edit` 能力，CLO-32）例外：沒兌換的也給真圖，擁有與兌換的規則不變（CLO-27）。
- 動態頭像（mp4）：現在穿哪套由衣櫃決定（輪流穿，或主人指定的「現在穿這套」，只有真的擁有的能穿；CLO-30），頭像與角色影片照現穿的那套（沒有現穿的 mp4 就沒有影片）。
- 使用者自己的角色、衣服、照片（只收 PNG、JPEG、WEBP；可以設成免點數）；官方角色的衣服與兌換條件不能改。

## 已知限制
- `.live.json`（WebGL 動態頭像）不做：舊家只剩兩個檔，且生圖影片的技能已封存那種做法（作者 2026-10-26 同意只做 mp4）。
- 不匯入舊資料（搬家當天轉）。隱藏版有哪些、圖放哪，由使用者自己決定（CLO-17）。全身照（`full/`）P6-4c 起支援（官方與我的同一段程式）。
- 不再有舊系統「每位最多 N 套」的上限（作者 2026-10-26 同意）；搬家轉資料時價格照舊規則（第一套 `cost: 0`、其他 `cost: 1`）。
- 兌換只認主人本人（`owner(web)`、`owner(cli)`）：秘書不能代替主人花點數（作者 2026-10-26 同意；舊系統的命令列誰都能兌換）。
- 剪影是霧面（16×16 的平均色），不是輪廓；WEBP 沒有剪影檔（標準庫解不開，不引入第三方），頁面畫灰色人形。
- 登記的套件啟用、停用不會觸發 vault 變更：動作最慢 5 分鐘（或下一次資料變更）才跟著出現或消失（CLO-33）。能力改了（`env` 換了），看板要等下一次重抓頁面清單（30 秒後才算過期，重新整理、切回視窗或重新進頁面時重抓）才跟著列或不列 `show_when` 的分頁。
- 能力紀錄停在最後寫的那份：衣櫃的程式停了（套件還開著），核心與頁面照舊讀那份；問 `system.get_mode` 偶爾失敗時那一輪當不是開發家，`edit` 拿掉，下一輪（最慢 5 分鐘）才回來（CLO-32）。
- 動作的登記是這個家的資料，不在登記的套件的資料夾裡：套件分享給別人，鈕不會跟著走，要對方的秘書再登記一次。`package` 欄位是登記的人自己寫的：使用者自己的套件之間，誰都能替別的套件名登記（家裡的程式互信，D-19；官方套件不能當登記者）（CLO-33）。
- 開發家沒兌換的衣服的真圖也在 `/pkg-files/closet/…`（CLO-27），跟擁有的真圖一樣沒有登入判斷；把正式家的 `env` 改成 `dev` 就等於全部不遮，`env` 只該寫在做角色與衣服的家。行程每一輪才問一次是不是開發家：改了 `env` 最慢 5 分鐘（或下一次資料變更）才換。
- 隱藏版開著的期間，它的圖就在 `/pkg-files/closet/…`，跟正常版的真圖一樣沒有登入判斷（tailnet 內知道網址就拿得到）；不想一直開著就用時段，或按完記得關。
- 換衣服後頭像下次載入才換（網址不變、`Cache-Control: no-cache` 讓瀏覽器重新驗證）；輪播以整點換；指定「現在穿這套」的那天不輪，過了午夜（機器的時區）那一輪回到輪流穿。
- 被偽造的 `closet.unlock` 會被封存，但 vault 封存後同一個編號不能再用：那一套之後兌換會被拒（原因「這套的兌換紀錄有問題，請跟任何一位秘書說」）。同理，封存了的衣服編號（以前展示間的「不要了」、之後 closet-mine 的刪一套）不能重用，新增請換編號。
- 人設／衣服移走後，該角色的 `person` 不封存而是清空（`outfits` 為空）：vault 沒有還原封存的做法，封存過的紀錄之後寫不進去。
- 使用者自己的角色與衣服由套件 `closet-mine` 加（`closet-mine.md`）；生圖秘書只在開發家（開發工坊 `admin` 的選用職位，ADM-39；CLO-23）。
