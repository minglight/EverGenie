# 模組：session（`internal/base/session`）

**目的：** 常駐 session 的生命週期：要開幾個、閒置／忙碌、把訊息送進 session（派送器）、每則訊息的回音、這一輪是誰觸發的與動作授權、引擎事件、討論串狀態、權限與問答的回送。
**種類：** 底層模組（`internal/base/`；沒有 HTTP、沒有指令，只給別人呼叫）

狀態檔欄位、`kind`、`state` 轉移表見 `schemas/session.md`；`Deliver`、事件、`AnswerApproval` 的介面語意見 `engine.md`。測試都在 `internal/base/session/`（假時鐘＋`Tick`、fake 引擎計數 `Deliver`，事件序列用 spike 錄的重放）。

## MUST
### 開、關、巡檢
- **SES-1** — 照 `agent.md` 的 `mode` 開主要 session（D-32）：`resident` 常駐，不在了在一個 watchdog 週期內重開；`ondemand` 第一句話來時派送器才開（話留在 `queued`），閒置 60 分鐘（`OndemandIdleClose`）收掉；當天有排程的（`SetScheduledToday`，接 `scheduler.ScheduledOn`）當天視為 `resident`；`none` 不開。測試 `TestWatchdogRestartsResident`、`TestOndemandStartsOnFirstMessage`、`TestScheduledDayIsResident`。
- **SES-2** — 常駐 session 開遠端存取（名稱 SES-55）；人名每次開都重讀，換人設後下次重開跟著換。測試 `TestRemoteAccessNameFollowsPersona`。
- **SES-3** — 可另開專屬 session：工作 session（SES-27）、待辦 `<職位>-r-<n>`、Goal 對話 `<職位>-<Goal 編號小寫>`（room，WEB-82）、主題對話、排程臨時；同名再開回同一個；閒置 `idle_close_after` 後收成 `stopped`（綁單的看單 SES-28；有話沒收尾的不收 SES-43），之後用 `engine_session_id` 接回。測試 `TestOpenRoomIdleCloseResume`。
- **SES-9** — 提供 `Rotate`：重開清 context、不帶舊 `engine_session_id`；何時叫由 `jobs` 決定（SCH-8）。測試 `TestRotateAfterNightly`。
- **SES-10** — 排程工作 2 分鐘送不進常駐就另開 `temp` 跑，閒置 30 分鐘收，同時最多 4 個、第 5 個排隊（認封包靠冪等鍵 `job:<id>#…`）。排程封包、`schedule.done`、夜間整理重開都歸 `jobs`；session 不讀 `job`、不訂 `schedule.fire`。測試 `TestRoutineTempAfter2Min`、`TestTempSessionCap4`。
- **SES-34** — 關一個核心記成 `stopped` 的 session（`Close`、`sessions stop`／`restart`）照樣叫一次引擎 `Stop`（舊結束事件晚到時引擎可能還開著）；不在的不算錯，找不到帳號的引擎直接回成功。測試 `TestCloseStoppedStillStopsEngine`。
- **SES-35** — 帳號巡檢：每 `WatchdogEvery` 讀名冊，這台啟用秘書綁的帳號（沒寫用 `accounts.default`）跟常駐對話的不同、且對話閒著（`idle`、沒待回答）就 `Rotate`；忙的下一輪再看。`open` 時記錄的帳號不同就不帶 `ResumeSessionID`。測試 `TestAccountChangeRestartsWhenIdle`。
- **SES-40** — `Deliver` 回 `gone`：照 `SESSION_ENDED` 記 `stopped`，那則放回 `queued`（不算失敗），派送器把主要 session 開回來（`MainReopenEvery` 30 秒內不重試；隨選照 SES-1）再送。測試 `TestGoneMarksStoppedReopensThenDelivers`、`TestReopenThrottled`。
- **SES-52** — 叫醒不等：停了的主要對話有主人的 chat，還沒叫過就馬上開（`MainReopenEvery` 只擋之後的重試）；工作 session 收到主人的 chat：`openQueued(force)`（不看 `work_max`；排隊中的另外收掉上限提問）。這些開法都是當場登記成 `starting`、等引擎在背景（SES-72），派送器不等。`Open` 帶 `Wake`（看板打開聊天頁）只叫醒啟用、在這台、resident／ondemand、停了或沒記錄的主要對話，其他回現況（沒記錄 `not_found`）。`ReceiveLatency` 給 doctor：今天、這台、主人的 chat，已收到的算 p50／p90，超過 3 秒、沒送到、還沒收到超過 3 秒的算 over。測試 `TestStoppedMainOpensImmediatelyForOwner`、`TestWakeOnChatOpen`、`TestOwnerOpensQueuedWorkBeyondLimit`、`TestReceiveLatency`。
- **SES-53** — 訂閱 `agent.changed`：收到就把 `watchdog`、`modesAt`、`accountsAt` 歸零，下一次 Tick（≤1 秒）重跑 30 秒一次的巡檢。測試 `TestAgentChangedRunsWatchdogNow`。
- **SES-55** — 遠端存取名稱：常駐 `<角色名>-<家的標籤>`（`platform.Home.Label()`＝`<owner>-<machine>`，開發家加 `@dev`），工作 session 再接 `-<單號>`；標籤空就只有角色名；同一角色也派給別的啟用秘書時補「·職位 id」（`輝夜·life-amy-home`）。Evidence: `state.go` → `remoteAccessName`、`remotePerson`；測試 `TestRemoteAccessNameUsesHomeLabel`、`TestRemoteAccessNameSharedPersonaAddsAgent`。
- **SES-56** — `BootPrompts`（引擎登記的、要主人出手才會動的提示：啟動對話框、話一直貼不進去）同時問每個沒停的 session 的引擎（有 `BootPrompts` 才問；問不到、每位 1 秒內沒回的略過，SES-72），依 session、提示編號排序，給健檢 `sessions.resident` 與看板。`AnswerBootPrompt` 先確認提示還在那個 session 上，再交給引擎按鍵，不在回 NotFound。Evidence: `bootprompts.go`；`TestAnswerBootPromptChecksPrompt`；`internal/feature/chat/checks_test.go` → `TestResidentCheckFlagsBootPrompt`。

### 引擎事件、狀態與確認
- **SES-4** — 狀態只由引擎的正規化事件決定（轉移表在 schema），不讀畫面、不猜卡住：沒有事件時狀態與每則話都不變（例外只有「不會再有事件來」的那幾種：SES-49 的額度恢復、SES-76、SES-77，D-69）；舊狀態檔的 `stuck` 當 `idle`。測試 `TestStateFromEngineEvents`、`TestNoEngineEventNoChange24h`、`TestStuckStateLoadsAsIdle`。
- **SES-6** — 實作 `EngineHostAPI`：`ReportEvent` 只更新狀態、交給派送器信箱、立刻回（不同步寫檔、P99 < 50 ms），不產生給模型的內容；`GetContext` 只在現況快照比上次附的新時回非空；核心不在時引擎照常運作。測試 `TestReportEventIsSilentAndFast`、`TestGetContextEmptyWhenUnchanged`。
- **SES-7** — `RequestApproval`（權限）：記成 `Pending`、`waiting`，看板對話的確認卡給「允許／拒絕」（只推播，SES-47）；`Resolve` 回給還在等的引擎並清 `pending`；逾時或核心沒接手回 `decided=false`、`Pending` 留著（SES-48）。可等 ≥10 分鐘，其他事件回報逾時很短。測試 `TestApprovalFlowAllowDeny`、`TestApprovalTimeout`。
- **SES-8** — `RequestApproval`（問題）：中立的 `Question` 顯示成按鈕；回答 `Decision.answers`（key＝`Question.text`；單選 label、複選「A, B」、自由輸入字串），多題全答完才 `Resolve`。測試 `TestQuestionButtons`、`TestMultiQuestionResolvesWhenAllAnswered`。
- **SES-48** — 確認逾時不消失（`native.go`）：到期限或引擎不等了，`handOff` 回 `decided=false`（核心要停或引擎的請求被取消時，`RequestApproval` 改回 `unavailable`，見 SES-66），`Pending` 留著、標 `native`，照舊 `waiting`、推播不收。主人 `Resolve`（含 `ResolveNotices`）native 的確認：題目答完後**放開鎖**叫 `Engine.AnswerApproval`（ENG-14），同一題同時只代答一次（再按 `CONFLICT`）；成功＝清 `Pending`、`busy`、照常回執、`applied=true`；`none`／`gone`＝清掉（`none` 回 idle）、`applied=false`；`unsupported` 回 `UNAVAILABLE`「這一題看板代答不了，請在秘書的對話裡回答（手機或網頁都行）」、確認留著；其他原因 `UNAVAILABLE`。引擎的下一個事件（`turn_started`、`activity_*`、`turn_ended`、`idle_hint`、`session_ended`、`rate_limited`）收掉 native 的確認（`idle_hint` 後回 idle、不蓋 `limited`）；還在等核心回答的不受 `idle_hint`／`activity_started` 影響。新的 `RequestApproval` 取代 native 舊確認。serve 重開讀回、沒停的 `Pending` 一律當 native（`restoreNative`）。測試 `TestTimeoutKeepsPendingWaitingNotStuck`、`TestTerminalAnswerClearsNativePending`、`TestNewApprovalReplacesNative`、`TestRestartRestoresNativePending`、`TestEngineAnswerReasons`。
- **SES-49** — 額度用完（`limited.go`）：`rate_limited` → `limited`、`limited_until`＝事件的 `until`、`state_since` 重設（已 limited 也重設）、清 `Pending`；`idle_hint` 不蓋。`requeueLimited`：還沒結束、經核心送的封包 `notified`／`received` 退回 `queued`（「額度用完，HH:MM 恢復後再送」），`working`／`blocked` 與這一輪的直接傳話記 `interrupted`、不重送。`limited` 時不送、不 `fallback`；`wait`＝`limited` 帶 `wait_until`；討論串 `limited`（優先在 `working` 前）。過了 `limitDue`（`limited_until`；零值用 `state_since`＋`LimitRetryAfter` 15 分鐘）記回 `idle` 叫醒派送器——「計時不改狀態」的例外，恢復時間是引擎給的事實。帳號巡檢把 `limited` 當閒著。補送時引擎回 `already`：記 `received`，等平台自己接著做那一輪的事件才收尾（等多久見 SES-76）；平台自己打的「continue」對不到封包時算補送那句的（沿用寄件人與 `origin`，不記 `last_owner`）。測試 `limited_test.go` → `TestRateLimitedRequeuesAndWaits`、`TestRateLimitedMidTurnNotResent`、`TestRateLimitedResumesAfterReset`、`TestRateLimitedPlatformResumeKeepsSender`。
- **SES-43** — 一輪停了就收（只看事件），對象是經核心送、還掛著 `received`／`working`／`blocked` 的話：`TURN_ENDED` 收這一輪的（SES-41），這個對話其他掛著的也記 `replied`；`IDLE_HINT`（處理完是 `idle` 才算，本來閒著也算；等確認、`limited` 不算）同 `TURN_ENDED`；`TURN_FAILED`、`SESSION_ENDED` 見 SES-57。沒事件不動。有話沒收尾的對話閒置不收。測試 `TestIdleHintSettlesInFlight`、`TestTurnEndedSettlesAfterCoreRestart`。
- **SES-57** — 一輪停了、話沒走完：`TURN_FAILED` → `idle`（不記 `last_turn_end_at`），這一輪與這個對話還掛著的話記 `interrupted`，原因是 `Error.Normalize()` 種類的白話（「AI 平台暫時忙不過來」「AI 帳號登入過期了」…，只講一遍、不寫「這一輪出錯了」），`last_message` 存平台原話；`session.messages[]` 的 `reason` 只給白話、平台原話另給 `reason_detail`（看板收在「詳細」）、種類給 `reason_kind`（auth、billing 看板不給「再說一次」，DEV-156 U-08）。`IDLE_HINT` 時還停在 `notified`、不是正在貼的：貼上比事件早的記 `failed`「這句還沒開始，可以重送」（不寫「她」：男角色也會看到，也不說「停下來」免得跟主人按「停」搞混），較晚的不動。`SESSION_ENDED` → 掛著的記 `interrupted`「對話結束了」（登出見 SES-64），`notified`（含 `delivered` 但她已 `stopped`）放回 `queued`、正在貼的等引擎回來；給她的直接傳話 `received` 還沒配到一輪的記 `interrupted`。`TURN_STARTED` 帶 `interrupted` 時這一輪的話和 `carried` 記 `interrupted`；`IDLE_HINT` 帶 `interrupted`（主人叫她停下）見 SES-62。`IDLE_HINT` 收尾沒有 `last_message` 時取這一輪開始後她最後一句，拿不到就空，秘書的 `say` 記 `replied` 不回空白。退避中那則送出前，同對話後面的話不插隊。不因這些事件發系統提醒或開單（notify 判斷）。Evidence: `origin.go` → `settleTurn`、`settleSession`、`claimPasted`、`directSent`；測試 `TestTurnFailedInterruptsWithReason`、`TestSessionEndedInterruptsInFlight`、`TestLaterMessageWaitsForEarlierRetry`、`TestReceipt*`。

### 派送器
- **SES-5** — 派送器把 `route: core` 封包送進 session：只在 `idle`（插話例外 SES-41）、沒有 `pending`、送前重讀狀態時才 `engine.Deliver`（完整文字，格式照 P3 計畫共通定案 15.）；同一個 session 同時只一則在 `notified`／`received`／`working`／`blocked`。測試 `TestDeliverOnlyWhenIdle`、`TestOneAtATime`、`TestRecheckBeforePaste`、`TestPastedTextFormat`。
- **SES-19** — 主人 3 分鐘內在這個 session 說過話，別人的封包先等；沒貼進去退避再試（SES-51）；不在了先接回（SES-40）；`kind: say` 排 5 分鐘就開同一位秘書的另一個工作 session `<職位>-c<n>`（`work`、不綁單、最多 2 個、不算 `work_max`、閒置 30 分鐘收；不再開 `clone`，D-33）；主人的 `chat`、`answer` 只進原 session。`Open` 的 `first_message` 當主人的 `chat` 交派送器，引擎不送第一句。測試 `TestOwnerQuietHoldsOthers`、`TestSayClonesAfter5Min`、`TestCloneCap2`、`TestOpenFirstMessageGoesThroughDispatcher`。
- **SES-41** — 主人插話（D-5）：主人的 `chat` 在 `busy`、沒 `Pending`、沒別則 `notified` 時也送（送 Enter 前仍檢查確認框），歷程記「插話」；`TURN_STARTED` 時上一輪沒結束也不是中斷，上一輪的封包（`carried`）跟這一輪一起記 `replied`；剛閒下 5 秒內不重貼。`WithMessages` 把還沒結束的封包（加主人 12 小時內失敗、沒重送的）填進 `Session.messages`。測試 `TestOwnerInterjectsWhileBusy`、`TestInterjectedTurnRepliesBoth`、`TestWithMessages`。
- **SES-51** — 排隊原因與重試（`receive.go`）：主人 queued／notified 的 chat 的 `wait` 依序：有 `Pending`／`waiting`＝`answer`；`limited`；`starting`，或 `stopped` 而派送器會開（主要對話要啟用、在這台、resident／ondemand；其他種類一律；沒記錄但隨選開得起來）＝`waking`；正在退避重試同一則＝`retrying`；`busy` 且這則是插話送的＝`interject`；同 session 有別則已貼上或收到還沒結束＝`busy`；說不出不填。`failed`（主人 12 小時內、沒重送）與 `interrupted`（12 小時內、之後主人沒再說、`last_turn_end_at` 沒晚於中斷）列出來帶 `reason`（`interrupted`＝原因＋「：」＋平台原話）。`Deliver` 回 `ok=false`：`dialog` 放回排隊（「她的畫面開著確認框，等你回答後再送」），1 秒最多試一次；`gone`→SES-40；`already` 記 `received`，併進進行中的一輪（`carried`）或替它開一輪（`adopted`）；其他（`paste`／`capture`／`enter`／呼叫失敗）轉回排隊退避（第 n 次等 0.5×2^(n-1) 秒，最多 `PasteRetryMax` 10 秒），不記失敗、不回音，原因寫歷程與 log。`TURN_STARTED`（`typed`）認封包：已貼上的與貼過正在重試的，內文前 40 字（不計空白）對得上優先，否則已貼上的第一則。主人的 chat 換狀態時推一次 session 狀態。測試 `TestRedeliverAlreadyDeliveredAdopted`、`TestDeliverTransientErrorsBackOff`、`TestDeliverDialogWaitsForAnswer`、`TestWaitReasonRetryingWhilePasteBacksOff`、`TestInterruptedHiddenAfterLaterTurnEnds`。
- **SES-71** — 貼上沒成功的 log 降頻（`dispatch.go` → `pasteRetry`、`pasteLogDue`；DEV-159）：同一則話前 3 次（`PasteLogFirst`）每次一行 WARN「貼上沒成功」，之後每 30 次（`PasteLogEvery`，退避到 10 秒後約 5 分鐘）一行，`try` 是累計次數；重試本身與寫進歷程的原因不變（SES-51）。超過 3 次之後貼進去，補一行 INFO「貼上恢復了」帶次數。連續貼不進去怎麼讓主人知道由引擎登記提示（SES-56 那條路）。測試 `receive_test.go` → `TestPasteRetryLogIsThrottled`。
- **SES-58** — 收件的對話不會在這台開起來就馬上記 `failed`「這台沒有這個對話」（`NoTargetReason`）：core 路線還在 `queued` 的話，① `Get` not_found、隨選也沒開、名稱不是這台叫得起來的秘書；或 ② 收件是停著的主要對話而秘書叫不起來（`cannotWake`：設定 not_found、停用、mode 不是 resident／ondemand；讀設定別的錯不算）。寄件人是秘書照 SES-20 回音；主人回答通知的 `answer` 這樣失敗不重送（`retryAnswers` 略過）。③ 收件對話的秘書停用了（`agentDisabled`，2026-11-07）：她的主要對話、房間與工作對話不管開著或停著都不貼、不叫起來（含排程寄去的）。存在的房間與工作對話（停了也算，秘書啟用時）、啟用的 resident／ondemand 秘書（主要對話沒建也算）照舊排著。Evidence: `dispatch.go` → `dispatch`；`receive.go` → `cannotWake`、`failNoTarget`；測試 `TestMissingTargetFailsRightAway`、`TestDisabledAgentRoomsFail`。

- **D-68** — 對話記錄裡工具呼叫的白話由引擎給（2026-11-03 QA，SES-65、ECL-53、WEB-125、WEB-126）：①`ChatMessage` 加 `tool_label`（只加不刪），跟 `activity` 同一張翻譯表，引擎套件寫一次、處理中的狀態字和對話記錄講的一樣；②原名 `tool` 不拿掉（指令列與舊資料要用、sdk 只加不刪）；③合併同一種、記次數是看板的事（怎麼排給人看），照顯示的字合併。否決：看板自己翻工具名（把某一家引擎的工具名綁進看板，違反 SES-63／法律第 3 條）；核心讀對話記錄時補白話（核心要認工具名）；把連續的同種工具在引擎端先合併（對話記錄是一則一則的事實，合併是畫面的事，別的用途〔指令列、配對 call_id〕會壞）。

- **D-69** — 「計時不改狀態」有例外，但只限「不會再有任何事件來」的情形（DEV-162，2026-11-17）。S5 拿掉所有計時是因為猜卡住會誤判；但引擎說話已經在對話裡、平台卻沒接著做時，沒有開始也沒有結束事件，那一則永遠掛著、同一個對話後面的話全部排著。決定：①只在她待命（引擎最後說的就是待命）時計時，忙著、等確認、額度用完一律不算；②到期的動作只有「放掉掛著的那一則」（退回排隊重送一次，再不行記中斷或沒送到），不動 session 的狀態、不重開對話、不往對話打字；③再不通就只發事實，由 notify 通知主人（SES-76、SES-77）。

## 已知限制
- 等引擎的時限（SES-72）管不到的：`Chat` 的跟讀串流（`follow`，本來就一直開著，跟著呼叫的人取消）；工作 session 名額提問回答「關掉 <單號>」時，關那一個是當場等（最多 `Stop` 的 20 秒）才接著開。時限到了只是核心放手，引擎那邊那個動作可能還在做：`Stop` 逾時後她可能其實已經關了或還開著，要等引擎回報才對得上。
- 測口吻花座位那個帳號的額度，誰都能呼叫、沒有用量上限；工作資料夾的專案設定仍會被一次性對話讀到。
- 狀態檔背景合併寫入：行程崩潰可能丟最後一次合併前的狀態，重啟後由引擎事件重建。
- 確認逾時後，notify 仍依 NTF-14 在兩小時後標 failed 請重答。
- 直接傳話何時送進收件方由平台決定，「主人正在聊不插話」只管 `route: core`。
- 本機 API 沒有身分驗證：授權擋的是模型判斷錯，不是冒用（秘書可以自己呼叫 API 冒用 `owner(…)`），D-24。
- 傳話分身是新的 context，看不到原 session 的對話。
- 工作 session 狀態檔沒有清理，單結束後記錄留著（`stopped`）。
- 模型與力度（SES-60）只跟著這段對話自己的引擎回報：同帳號別的對話改了帳號的預設（D-46 ④），這段要等她下一輪做完、引擎回報了才換。
- hot cache 倒數只在看板算（`last_turn_end_at` 起 60 分鐘），核心沒有快取到期事件。
- 額度恢復後補送那則，引擎說「已經在她的對話裡」才記 `received` 等平台接著做；平台沒說會自己接著做的，engine-claude 不回 `already`、照常重貼（ECL-39，DEV-102）。平台說了會接著做、後來卻沒做（例如有人按 esc 取消）時，照 SES-76 的期限作廢重送。
- 總保險（SES-77）只看核心記成待命的對話：核心記成忙著、其實平台已經停了的（結束事件丟了又沒有 `IDLE_HINT`）不在範圍；停了開不起來的看 `sessions.resident`。卡住清單與「這一次」的記錄只在記憶體：核心重開後重新算（自救過的那一段不記得，可能再自救一次才報）；啟動後第一輪當下不符合條件的（例如她的對話還在啟動），舊提醒會先收掉、再滿條件時重發一次。排著的話全部被記成沒送到／沒做完之後不再列為卡住（各則自己顯示結果），對話本身是不是好的要等下一句才知道。作廢的記錄與「一定重貼」的記號（SES-76）不存檔：作廢後核心重開、平台才接著做的那一輪會記成主人打字；退回排隊後還沒重貼核心就重開，引擎會再說一次已經在了、再等 3 分鐘，這時算自救過、改走查對話記錄收尾。
- 到期重貼（SES-76）可能讓同一句做兩次：重貼之後平台才自己接著做原本那句（兩邊都會跑）。每次額度恢復最多重貼一次。
- `giveUp` 讀對話記錄只看「那句之後最後一則是不是她說的話」：她說了一句話、其實還沒做完就停住的，會記成已回覆；對話記錄裡同一句出現多次時看最後一次。
- 作廢後、重貼前平台先自己接著做了那句：那一輪記成原寄件人但不掛回封包，封包照常重貼，同一句會做兩次。作廢記錄的原寄件人是主人時，那一輪不更新「主人最後說話」的時間。
- 核心與引擎套件版本不一致（引擎不認得 `force`）時，到期重貼會再得到 `already`，改走查對話記錄收尾。
- `VoidedKeep` 內主人剛好直接打字的那一輪會記成原寄件人（比較嚴的那邊：可能多問他一次確認）。
